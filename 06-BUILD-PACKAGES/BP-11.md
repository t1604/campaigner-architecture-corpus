One-Time End Condition & Closure

0. Purpose and Build Boundary
Implement deliberate, verifiable closure for every One-Time campaign so bounded advertising ends on its defined End Condition or explicit authorized stop, never merely when someone remembers to stop it.
This package is a requirements artifact. It may propose concrete schemas/interfaces only as DRAFT implementation candidates. It does not authorize coding, deployment, runtime writes or Meta writes.


1. Canonical Coverage
Stages: B8.
Contracts: C14; C11 for closure readback; C13 handoff to final measurement.
Primary domain/core ownership: Execution Orchestration owns operational closure; Meta owns current platform state/capability; Advisor owns professional/user-facing closure; user/approved End Condition supplies authority as applicable.
Dependencies: BP-00, BP-08, BP-09; hands off to BP-10; BP-12 overlay for pilot.


2. Functional Requirements
FR-11.1 Represent End Condition from campaign creation and carry it through managed run.
FR-11.2 Support conceptual condition classes: date/time, event/offer end, spend limit, inventory/capacity, sold/rented/closed objective, user stop, responsible stop or other scoped condition.
FR-11.3 Detect approaching/met condition and surface closure decision/status.
FR-11.4 Distinguish predefined closure authority from discretionary material change; never extend scope autonomously.
FR-11.5 Execute stop/close through BP-08 protected execution path.
FR-11.6 Verify final live state/readback and final spend.
FR-11.7 Surface unresolved obligations/assets/provider states.
FR-11.8 Handoff final scope/spend/timeline/closure state to BP-10.
FR-11.9 Support closure failure/recovery without silent campaign extension.


3. Non-Functional / Governance Requirements
Timezone-safe scheduling; closure triggers idempotent; no accidental reopen from retries; final state audit durable; alerting before/at end where operationally useful; Human Review for discretionary/material closure/recovery in pilot.


4. Conceptual Data Objects and Relationships
EndCondition; EndConditionEvaluation; ClosureDecision; ClosureAction; FinalReadback; FinalSpendSnapshot; OutstandingObligation; ClosureSummaryHandoff.

6. API / Integration Requirements
evaluateEndCondition; notifyApproachingEnd; request/recordClosureDecision; executeClosure via BP-08; verifyClosure; listOutstandingObligations; createFinalMeasurementHandoff.


7. Prompt / Model / Tool Responsibilities
Advisor may explain whether a condition is met/ambiguous and propose responsible closure/extension options. Model cannot autonomously extend the campaign or reinterpret End Condition beyond its approved meaning.
Prohibited: private chain-of-thought storage; silent authority expansion; turning Prior into Local Truth; silent strategy/brand/budget/measurement changes outside the owning Core.


8. UI / Workbench Requirements
One-Time campaign shows end condition and remaining time/budget during run; approaching-end notice; clear closed/closing/uncertain status; user can request explicit extension/change which routes back to scope decision rather than silently continue.


9. Authority / Consent / Human Review Gates
Pre-approved End Condition may authorize only the defined closure mechanics according to approved downstream contract. Extension or discretionary material change requires new user decision/authorization. Human Review for material/discretionary closure in pilot.
Pilot default: 100% Human Review for material professional/execution decisions covered by this package.


10. Context / Knowledge Projection Interfaces
Closure receives exact End Condition, live campaign state, remaining spend, obligations and applicable authority only; no need for full strategy/context.


11. Evidence / Event / Readback Requirements
End Condition version/evaluations, closure trigger/decision/authority, stop execution/readback, final spend/state, unresolved obligations and final handoff refs.


12. Metrics / Measurement Requirements
Missed/late closure, closure execution/readback success, campaign live past end condition, discretionary extensions, final spend variance and unresolved obligations.


13. Failure / Recovery / Rollback / Semantic Return
Ambiguous End Condition→Advisor/Director Return; closure API failure→retry/readback/recovery via BP-08; uncertain final state remains uncertain; event/offer extension→reopen B1/B2/B3 as appropriate, not auto-extend.


14. Security / Privacy / Multi-Business Isolation
Closure target/account/business validation; least-privilege Meta tokens; no unrelated campaign stop; user instruction authenticated and scoped.


15. Tests
Date end closes once; duplicate trigger no duplicate stop; campaign cannot silently run past met condition; extension requires new decision; readback mismatch remains uncertain; wrong campaign target blocked; final handoff reaches BP-10.


16. Acceptance Criteria
AC-11.1 Every One-Time campaign has an explicit End Condition before launch.
AC-11.2 End Condition is evaluated throughout run.
AC-11.3 Campaign cannot extend beyond approved scope automatically.
AC-11.4 Closure uses controlled execution and verified readback.
AC-11.5 Final state/spend/obligations are captured.
AC-11.6 BP-10 receives complete final evidence package.


17. Migration / Compatibility
Existing one-time campaigns without End Condition must be flagged incomplete/legacy and require explicit condition before new pilot writes; do not invent end dates from history.


18. Deferred / Open Decisions
Exact End Condition enum, scheduler/automation implementation, notification cadence, extension pricing/policy, platform-specific stop semantics.
Deferred items are not silently treated as defaults. Any blocker status must be explicit.


19. Traceability
Owner-approved One-Time Flow End Condition doctrine → Stage Truth B8 → C14/C11/C13 → BP-11.
Every implemented requirement must map back to approved Truth/Core/Flow/Stage/Contract and forward to a test/evidence requirement.

21. OWNER-APPROVED END-CONDITION / EXTENSION / DEFAULT CLOSURE SEMANTICS
Owner Decision source: CAMPAINER-F5-END-CONDITION-CLOSURE-OWNER-DECISION-001 — APPROVED — ID 1LXPly_A-eqHalvr8MwcG8Kdm1wPcooufipdhKFcUOXg.


21.1 Campaign envelope. Every One-Time campaign must carry an approved media-budget cap and any hard date/event boundary that materially limits the live period.
21.2 Pre-end notice. Campainer must notify the user before expected end and offer an explicit extension path. Exact lead time/cadence/channel remain Build/Experience details and are not Product Truth.
21.3 Silence is not consent. No response does not extend budget/time/scope and does not authorize continued spend.
21.4 Default closure. If no extension is explicitly approved/authorized, close when the approved media-budget cap is exhausted. If a hard approved date/event boundary occurs earlier, close at that earlier boundary even if budget remains.
21.5 Extension governance. Any extension that changes budget, time window, scope, objective or material campaign meaning creates a new governed decision/version and must pass applicable Human Review, approval/authorization and Fresh Preflight before new live writes.
21.6 Deterministic pilot classes. Exact approved budget cap and objectively testable hard timestamp/event deadline may be evaluated deterministically for closure. Sold/rented, inventory/capacity exhausted, business objective achieved and responsible-stop conditions remain review-triggering/non-deterministic unless a later governed class contract proves exact semantics and authority.
21.7 Ambiguity. Ambiguous, contradictory, stale or insufficient evidence never silently extends and never claims closure certainty. Route to Human Review/Semantic Return/pending closure while enforcing any hard pre-approved boundary.
21.8 Protected execution. Closure actions use BP-08 protected execution/readback semantics. Provider receipt alone is not verified final state.
21.9 Notification failure. Failure to deliver the pre-end notice never creates authority to continue spending; hard approved boundaries still govern.
21.10 Mandatory tests added: no-response does not extend; budget cap closes once/no overspend; earlier hard date wins over remaining budget; explicit extension creates new governed version/authority; notification failure still closes at boundary; ambiguous sold-out/business-goal state does not auto-close/extend; duplicate end trigger is idempotent; closure readback uncertainty remains explicit.


22. OWNER-APPROVED USER-STOP / UNUSED MEDIA BALANCE SEMANTICS
Owner Decision source: CAMPAINER-ONE-TIME-UNUSED-MEDIA-BALANCE-OWNER-DECISION-001 — APPROVED / LEGAL-FINANCE RELEASE GATE — ID 1-kiC1QKNgeqwpuKdfC_cto8J1JwFz-wAAaYqNKiJF7Q.
Related hard invariant: CAMPAINER-MEDIA-FUNDING-NO-CREDIT-EXPOSURE-OWNER-DECISION-001 — ID 1VMKuxBFX7nJNG5_wh7-cRyE_irEojEEAr8tCu5V4HVY.


22.1 User stop. An authenticated user instruction may close a One-Time campaign before budget-cap exhaustion. The stop uses BP-08 protected execution/readback and never implies automatic refund or forfeiture.
22.2 Final exposure first. Before unused balance is calculated, the system must establish verified closure/final spend and determine the protected coverage floor for all settled/unsettled Meta exposure, lag, reversals and disputes.
22.3 Residual balance. Only the amount safely above that coverage floor is an eligible unused media remainder. It must become a segregated user-identified exact-ScopeRef media balance preserving source-payment/campaign/closure lineage.
22.4 No mixing/reuse. The residual balance cannot become service/AI/management revenue, another user's funding, or another campaign's spend automatically. Funding Balance ≠ Spending Authorization.
22.5 Refund request. During the applicable safety/claim period, the user may request return of the eligible balance. Refund execution cannot reduce protected coverage below outstanding Meta obligations.
22.6 Safety clock. The claim/safety period begins only after verified closure and sufficiently known Meta exposure/settlement state; pressing Stop alone does not start the clock.
22.7 Owner intent after no claim. After the lawful approved safety/claim period, if the user has not requested return, the remaining balance may become releasable to Campainer only after a separate Legal/Finance gate closes the exact lawful period, contractual disclosure/consent, consumer/payment-services/unclaimed-funds treatment, required notices, accounting/tax and licensing/segregation requirements.
22.8 No time-only revenue conversion. Until the Legal/Finance gate is closed, time elapsed alone cannot convert the balance into Campainer revenue.
22.9 Dispute/chargeback. Disputed media funding is not spendable coverage, may require immediate hold/stop, and cannot accelerate transfer of residual balance to Campainer.
22.10 Future use. Reusing the residual balance for another campaign requires explicit user instruction and the applicable fresh Media/Budget decision/authorization.
22.11 UI/evidence. Closure UI/workbench must show final spend, outstanding exposure/coverage floor, eligible residual balance, refund-request state and Legal/Finance release-gate state; no false “available to Campainer” status before legal release eligibility.
22.12 Mandatory tests: early user stop leaves unused remainder in user-identified balance; Meta lag reduces eligible remainder; refund request preserves coverage floor; wrong scope cannot claim/use balance; later campaign cannot silently spend rollover; elapsed time with legal gate open does not create revenue; chargeback removes disputed funding from spendable coverage and blocks accelerated release.
22.13 Acceptance additions. AC-11.7 Early user closure preserves an exact user/scope unused-media balance after Meta obligations are covered. AC-11.8 No unused One-Time media balance becomes Campainer revenue before the approved Legal/Finance release gate. AC-11.9 Funding availability never substitutes for new spending authorization.
