0. Purpose and Build Boundary
Implement the protected transition from approved professional package to explicit scoped authorization, fresh preflight, controlled Meta/provider execution and verified readback, with no Shadow Decision and no authority inferred from payment, approval or capability.
This package is a requirements artifact. It may propose concrete schemas/interfaces only as DRAFT implementation candidates. It does not authorize coding, deployment, runtime writes or Meta writes.


1. Canonical Coverage
Stages: A9, B6; also material live changes from A10/B7.
Contracts: C09, C10, C11, C16.
Primary domain/core ownership: Execution Orchestration primary; Meta owns current platform capability/state; User/authorized owner grants authority; Context stores verified operational state; Advisor/Experience handle user-facing authorization/status.
Dependencies: BP-00, BP-07; BP-12 overlay required before pilot authority.


2. Functional Requirements
FR-08.1 Create explicit Authorization against exact approved package/action version, target and spend/scope envelope.
FR-08.2 Run Fresh Preflight close to execution checking target identity, permissions, dependencies, assets/destination, current state, capability/eligibility and conflicts.
FR-08.3 Build closed semantic Action Contract from authorized intent.
FR-08.4 Execute only through permitted Meta/provider adapter and preserve idempotent operation identity.
FR-08.5 Separate execution attempt/provider receipt from Verified Readback.
FR-08.6 Read back live state where available and persist verified/unverified/partial state explicitly.
FR-08.7 Detect discrepancies, partial success and non-equivalent fallback; Return upstream when meaning changes.
FR-08.8 Support recovery/rollback only inside preserved authority/semantic equivalence; otherwise new decision/authorization required.
FR-08.9 Write verified operational state to Context.
FR-08.10 Human Review gates every material pilot live write and semantics-affecting recovery.


3. Non-Functional / Governance Requirements
Fail closed on missing/ambiguous authority; strong idempotency; retries observable; live-state freshness explicit; provider secrets least privilege; audit trail durable; no eventual-success assumption without readback; execution adapters isolated from professional strategy logic.


4. Conceptual Data Objects and Relationships
AuthorizationRecord; ActionContract; PreflightResult; ExecutionAttempt; ProviderReceipt; ReadbackResult; LiveStateSnapshot; RecoveryAction; RollbackAction; Discrepancy; SemanticReturn.

6. API / Integration Requirements
request/grant/revokeAuthorization; createActionContract; runFreshPreflight; executeAuthorizedAction; queryExecutionStatus; readbackLiveState; registerDiscrepancy; requestRecovery/Rollback; createSemanticReturn. Meta/provider adapter APIs versioned behind internal interface.


7. Prompt / Model / Tool Responsibilities
Models may explain authorization scope, summarize preflight and propose recovery options. Models may not authorize, expand scope, select closest-valid actions with changed meaning or fabricate live state. Tool write access only after authorization + Human Review gate.
Prohibited: private chain-of-thought storage; silent authority expansion; turning Prior into Local Truth; silent strategy/brand/budget/measurement changes outside the owning Core.


8. UI / Workbench Requirements
Authorization surface shows exact action/package, target, budget/spend scope, material state change and what is not authorized. Execution status distinguishes queued/attempted/receipt/readback/verified/uncertain/failed. Recovery requires explicit review when semantics/risk changes.


9. Authority / Consent / Human Review Gates
Explicit scoped Authorization mandatory. Approval, payment, account connection and capability are insufficient. Material pilot writes require Human Review. Any scope/meaning change invalidates or narrows prior authority and routes upstream.
Pilot default: 100% Human Review for material professional/execution decisions covered by this package.


10. Context / Knowledge Projection Interfaces
Executor receives approved/authorized intent, exact target/scope, budget authority, protected constraints, required live-state/context, dependencies and expected state — not whole strategy discussion.


11. Evidence / Event / Readback Requirements
Authorization actor/time/scope/version; Human Review; preflight checks/freshness; execution idempotency/receipt; readback evidence; discrepancies; recovery/rollback; final verified or explicitly uncertain state.


12. Metrics / Measurement Requirements
Authorization blocks, preflight failures, execution success vs verified success, discrepancy/partial rates, recovery/rollback, stale-state failures, unauthorized-write attempts. Technical success is not marketing success.


13. Failure / Recovery / Rollback / Semantic Return
Missing authority→block; stale capability→re-preflight; provider timeout→safe status query/retry with idempotency; partial success→readback/discrepancy and review; non-equivalent recovery→Semantic Return; unknown final state must remain Unknown, not marked success.


14. Security / Privacy / Multi-Business Isolation
OAuth/token secrets isolated; least-privilege scopes; no writes to wrong Business/ad account; target ownership validation; audit every credentialed action; sensitive provider responses minimized; BP-12 security controls mandatory for pilot.


15. Tests
Approval-only write blocked; payment-only write blocked; expired/stale preflight blocked; duplicate retry produces one material action; receipt without readback remains unverified; readback mismatch triggers discrepancy; non-equivalent fallback triggers Return; wrong account/business target blocked.


16. Acceptance Criteria
AC-08.1 Every material live write has explicit scoped authorization and Human Review in pilot.
AC-08.2 Fresh Preflight occurs before action.
AC-08.3 Provider receipt is never treated as verified live state.
AC-08.4 Retries cannot duplicate material actions.
AC-08.5 Non-equivalent fallback cannot execute silently.
AC-08.6 Verified operational state/uncertainty is persisted and traceable.


17. Migration / Compatibility
Existing Meta connections/imported live state may be read as capability/context but never as standing write authorization. Legacy execution logs should be preserved as historical evidence with verification status unknown if no readback exists.


18. Deferred / Open Decisions
Exact Meta Graph API/object details, provider version, idempotency/retry/backoff/timeouts, final rollback mechanics, authority risk tiers, future bundled low-risk authority.
Deferred items are not silently treated as defaults. Any blocker status must be explicit.


19. Traceability
Authority-State Contract + Meta/EO Cores → Stage Truth A9/B6 → C09/C10/C11/C16 → BP-08.
Every implemented requirement must map back to approved Truth/Core/Flow/Stage/Contract and forward to a test/evidence requirement.

21. OWNER-APPROVED EXTERNAL-REVIEW REMEDIATION — AUTHORITY NORMALIZATION
21.1 Canonical ownership. BP-08 AuthorizationRecord is a typed authorization extension/projection of BP-00 v1.1 canonical AuthorityRecord. It must reference the canonical authority identity and current canonical state; it is not a separate source of truth or independently revocable persistence record.
21.2 Authorization APIs. request/grant/revokeAuthorization are domain-specific interfaces over the BP-00 canonical authority lifecycle. grant creates/updates the canonical AuthorityRecord through governed semantics; revoke/supersede must affect the canonical record observed by every execution check.
21.3 Validity predicate. Before createActionContract and again at execution preflight, authority must be VALID for the exact subject/version, action class, target, scope, spend/budget bounds and attributable actor/grant basis; it must not be revoked, superseded or expired and must satisfy applicable freshness. Missing, stale, ambiguous or mismatched authority cannot execute.
21.4 Human Review is independent. A HumanReviewRecord may be required by BP-12 registry for a material live write, but review approval neither creates nor expands Authorization. Execution requires both valid authority and every independently required review gate.
21.5 Tests added. Revoke through BP-00 invalidates BP-08 execution immediately; superseded version cannot execute; wrong target/scope/budget fails; stale authority/preflight fails; BP-08 cannot create a parallel authorization that survives canonical revocation; Human Review without authority cannot execute; authority without required Human Review cannot execute in pilot.
21.6 Acceptance additions. AC-08.7 Every Authorization resolves to one BP-00 canonical AuthorityRecord. AC-08.8 Authorization validity is objectively checkable and fail-closed across lifecycle events.
21.7 Remaining external-review condition. VERIFIED live-state semantics still require an action-class Verification Contract Registry before F4/live-write implementation acceptance. Until that registry exists, provider receipt remains unverified and any non-provable resulting state remains UNVERIFIED or UNKNOWN; no adapter may choose VERIFIED by convention.
