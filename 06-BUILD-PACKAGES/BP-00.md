CAMPAINER-BUILD-PACKAGE-BP-00-001 — v1.1
Shared Semantic Runtime & Governance Foundation

0. Purpose and Build Boundary
Build the shared semantic and governance substrate used by every Campainer path: scoped identity, authority separation, evidence/decision lineage, Shared Work Objects, Human Review routing, Unknown/Freshness/Scope preservation, Semantic Return/Reopen and multi-business isolation. It must prevent each vertical slice from inventing its own truth, authority or audit model.
This package is a requirements artifact. It may propose concrete schemas/interfaces only as DRAFT implementation candidates. It does not authorize coding, deployment, runtime writes or Meta writes.


1. Canonical Coverage
Stages: Cross-stage; supports ENTRY, A1–A11 and B1–B9.
Contracts: C16 mandatory; shared semantics underpin C01–C15.
Primary domain/core ownership: Complete User Context owns local truth; Experience presents state; Advisor remains the user-facing identity; Director owns bounded decision frames; domain owners remain unchanged.
Dependencies: Canonical Product Flow v1.0; Flow Core Applicability Matrix v1.0; Stage Truth Master v1.0; Decision & Handoff Contracts Master v1.0. BP-01 and all later packages depend on this foundation.


2. Functional Requirements
FR-00.1 Represent scoped identities for User, Business, Offering, Campaign, One-Time Campaign and related Work Objects without cross-business leakage.
FR-00.2 Represent the shared Work Object families: Information/Knowledge Need; Professional Work; Authority; Outcome/Learning; Return/Reopen.
FR-00.3 Preserve explicit state distinctions for Recommendation, User Choice, Approval, Authorization, Execution and Verified Readback.
FR-00.4 Record governed lineage links among evidence, decision, intervention, execution and result.
FR-00.5 Support Semantic Return targeting the owner of broken meaning, with what remains valid and what must be reconsidered.
FR-00.6 Support Reopen routing to the professional Stage/domain that owns the reopened decision.
FR-00.7 Support Human Review request/result state for material pilot decisions.
FR-00.8 Preserve Unknown, contradiction, freshness and scope as first-class semantic states rather than coercing them to null/zero/fail.
FR-00.9 Enforce active Business scope and explicit cross-business inheritance only.


3. Non-Functional / Governance Requirements
All material state changes must be auditable; lineage must survive retries and partial failures; no private chain-of-thought storage; state transitions must be idempotency-friendly; active Business scope must be explicit; authority checks must fail closed; Unknown must remain representable; package must support controlled-pilot Human Review without changing domain ownership.


4. Conceptual Data Objects and Relationships
Conceptual objects: ScopeRef; WorkObject; AuthorityRecord; EvidenceRef; DecisionRef; InterventionRef; ExecutionRef; ReadbackRef; HumanReviewRecord; SemanticReturn; ReopenRequest; VersionRef. Relationships: every material WorkObject belongs to one active scope; authority references exact subject/version/scope; execution references authority; readback references execution; result/learning links back to intervention and evidence.


5. Proposed Concrete Schemas — DRAFT / NOT APPROVED
Candidate tables/documents: scope_ref(id,type,parent_scope_id,business_id); work_object(id,scope_id,family,owner_domain,status,version); authority_record(id,scope_id,subject_ref,authority_kind,actor_ref,granted_at,revoked_at); lineage_edge(from_ref,to_ref,relation); semantic_return(id,source_ref,target_owner,reason_code,valid_refs,broken_refs); human_review(id,subject_ref,reviewer_ref,status,decision_ref). Exact enums and persistence form remain DRAFT.
Schema rule: IDs, fields, enums, indexes and persistence mechanics remain DRAFT until separately approved. No inferred field is canonical merely because it appears here.


6. API / Integration Requirements
Internal interfaces: resolveActiveScope; create/update WorkObject with optimistic/version checks; request/record Human Review; grant/revoke/check scoped authority; append lineage edge; create Semantic Return/Reopen; query trace by subject. APIs must never infer authority from payment, capability or prior approval.


7. Prompt / Model / Tool Responsibilities
Models may summarize governed state, classify a requested Work Object family, propose Return reasons and explain authority state. Models may not mint authority, silently switch Business scope, promote evidence to truth, or write hidden reasoning. Tool permissions are read-first unless a later package explicitly authorizes a write.
Prohibited: private chain-of-thought storage; silent authority expansion; turning Prior into Local Truth; silent strategy/brand/budget/measurement changes outside the owning Core.


8. UI / Workbench Requirements
Shared UX primitives: active Business/scope indicator; status chips for Recommendation/Approval/Authorization/Executed/Verified; Human Review pending/approved/rejected; visible Unknown/constraint notices; Return/Reopen task; trace/status surfaces understandable to the user without exposing internal chain-of-thought.


9. Authority / Consent / Human Review Gates
Authority must be explicit, scoped, attributable and version-linked. Human Review is required for material pilot decisions. A user-facing approval surface cannot by itself create live-write authority. Business-scope switching requires explicit context change, not inference.
Pilot default: 100% Human Review for material professional/execution decisions covered by this package.


10. Context / Knowledge Projection Interfaces
Define reusable projection envelopes carrying identity/scope, local truth refs, Knowledge/Evidence refs, Unknowns, freshness, authority state, protected constraints, receiver discretion and Return conditions. Projection is a reference/view, not ownership transfer or whole-context copy.


11. Evidence / Event / Readback Requirements
Append-only or equivalently immutable audit semantics for material transitions; record actor/source, subject/version, previous/new state, authority basis, review result and trace refs. Readback remains distinct from execution receipt. Correction events preserve prior history.


12. Metrics / Measurement Requirements
Operational governance metrics only: missing authority blocks, unresolved Returns, Human Review coverage, cross-business isolation violations, trace completeness and verified-vs-unverified execution state. These are system-control metrics, not business-performance truth.


13. Failure / Recovery / Rollback / Semantic Return
Fail closed on ambiguous scope/authority; preserve partial state; retry must not duplicate authority or material actions; Return when required meaning is missing; Reopen to owning Stage when later evidence invalidates a decision. Recovery cannot silently create a substitute action.


14. Security / Privacy / Multi-Business Isolation
Tenant/user/business scope separation; least privilege; sensitive evidence access scoped to need-to-know; no cross-business asset/truth transfer without explicit relationship; audit access controlled; retention/deletion hooks must preserve required governance lineage while honoring later privacy policy.


15. Tests
Unit: authority-state transitions, scope isolation, Return/Reopen routing, lineage creation. Integration: approval without authorization cannot execute; receipt without readback remains unverified; switching businesses does not leak context/assets. E2E golden cases for both branches with Human Review. Negative tests for stale/unknown/contradicted state.


16. Acceptance Criteria
AC-00.1 No material live action can pass without an explicit authority record.
AC-00.2 No cross-business read/write occurs without explicit allowed relation.
AC-00.3 Every material execution can be traced to a decision and authority or is marked invalid/blocked.
AC-00.4 Unknown/Return/Reopen are representable and do not collapse to generic error.
AC-00.5 Human Review can gate every material pilot decision class.
AC-00.6 Later packages reuse this foundation instead of creating parallel authority/context/evidence systems.


17. Migration / Compatibility
Historical Campainer objects may require mapping into scoped refs and lineage without rewriting history. Existing approvals/payments must not be imported as live authorizations. Migration design is deferred until current runtime storage is inspected.


18. Deferred / Open Decisions
Final DB engine/schema, exact enums/status codes, event-bus design, retention periods, risk tiers, low-risk bundled authority, final auth provider, immutable-log implementation, production scale.
Deferred items are not silently treated as defaults. Any blocker status must be explicit.


19. Traceability
Constitution/Product Truth → Final Core Architecture §§4–6,15 → all Stage Truth cross-stage invariants → Contracts C09–C16 especially C16 → BP-00 FR/AC/tests. Each later BP must reference BP-00 requirements it consumes.
Every implemented requirement must map back to approved Truth/Core/Flow/Stage/Contract and forward to a test/evidence requirement.

21. OWNER-APPROVED EXTERNAL-REVIEW REMEDIATION — F0 GOVERNANCE SEMANTICS
STATUS: OWNER-APPROVED BUILD REQUIREMENT SEMANTICS. SCHEMA AUTHORITY: NO. BUILD AUTHORITY: NO.
21.1 Canonical primitive ownership. BP-00 is the sole canonical Build-layer owner of ScopeRef, AuthorityRecord, HumanReviewRecord, Audit/Trace identity and VersionRef. BP-specific records may be typed extensions or projections referencing these canonical identities and states; they must not create parallel truth/persistence ownership.
21.2 Canonical ScopeRef. Every material WorkObject resolves to one explicit ScopeRef. Valid scope types include User, Business, Offering, Campaign and One-Time Campaign. A One-Time Campaign may exist without a Business under an explicit user-owned One-Time Campaign scope. Later attachment to a Business is an explicit governed relationship; it is never inferred, never silently reparents history, and never creates cross-business inheritance.
21.3 Authority validity. Authority is VALID only for the exact subject/version, action class, target, scope, bounds and actor/grant basis for which it was granted, while not revoked, superseded or expired and while required freshness conditions remain satisfied. Absent, stale, ambiguous or mismatched authority is INVALID or UNKNOWN and cannot execute. Human Review is a separate gate and never becomes authority by itself.
21.4 Human Review identity. HumanReviewRecord is the canonical immutable review-result identity. Queue/control-plane lifecycle may reference it but cannot create a second approval truth.
21.5 Pilot Material Decision Registry. Material families are Strategy; Creative claim/meaning; Brand Truth change; Media/Budget; Launch/live write; Recovery/rollback; Business Intervention; Measurement/Causal Interpretation; Learning promotion/reuse; Closure/extension. Each runtime material decision must map to a registry class and to a qualified human reviewer for the owning professional/operational domain. During pilot, UNCLASSIFIED decision class means REVIEW REQUIRED / BLOCKED until classified. A model/automation cannot be the approving reviewer.
21.6 Epistemic-state convention. UNKNOWN = value/truth not known. MISSING = expected value/evidence absent. UNVERIFIED = reported/observed state exists but the required verification predicate has not been satisfied. NOT_APPLICABLE = the value/decision has no semantic applicability in the current scope. None of these states equals zero, false, fail or each other.
21.7 Critical audit failure. No material external write begins unless durable pre-write governance evidence exists for intent, scope, authority identity/state, required Human Review result and a pre-issued operation identity. If durable pre-write evidence cannot be established, block. If provider action may already have occurred and post-write evidence persistence fails, state becomes UNKNOWN / RECOVERY_REQUIRED, never normal success; recovery uses the pre-issued operation identity plus authoritative readback.
21.8 Mandatory F0 tests. PASS requires: revoked/superseded/stale/mismatched authority cannot execute; BP-specific authorization resolves to canonical AuthorityRecord; One-Time-without-Business scope cannot leak to a Business; later Business attachment is explicit and preserves history; every registry class is review-gated; UNCLASSIFIED is blocked; BP-12 queue result resolves to canonical HumanReviewRecord; durable pre-write audit failure blocks; possible post-write logging failure yields UNKNOWN/RECOVERY_REQUIRED; UNKNOWN/MISSING/UNVERIFIED/NOT_APPLICABLE round-trip distinctly.
21.9 Acceptance additions. AC-00.7 One canonical primitive identity exists for scope, authority, review, audit/trace and version across all BPs. AC-00.8 Authority validity is objectively checkable and fail-closed. AC-00.9 All pilot material-decision classes are deterministically review-gated, including unclassified fail-closed. AC-00.10 Critical external writes cannot begin without durable governance evidence and operation identity. AC-00.11 Epistemic states remain semantically distinct end-to-end.
