CAMPAINER-BUILD-PACKAGE-BP-03-001 — v1.1
Business/Ongoing Pre-Payment Journey
STATUS: OWNER-APPROVED BUILD REQUIREMENTS
BUILD AUTHORITY: NO
RUNTIME AUTHORITY: NO
META WRITE / LAUNCH AUTHORITY: NO
PRODUCT OWNER AUTHORITY: PRESERVED
DERIVES FROM: CAMPAINER-BUILD-PACKAGES-MASTER-001 v1.0 + applicable Canonical Flow / Stage Truth / Contracts / Domain Cores.


0. Purpose and Build Boundary
Implement A1–A3 as a coherent pre-payment journey: adaptive Short Diagnosis → real Strategy Initial value with three insights and Route Recommendation → informed service-scope choice and payment, while preserving professional truth and authority separation.
This package is a requirements artifact. It may propose concrete schemas/interfaces only as DRAFT implementation candidates. It does not authorize coding, deployment, runtime writes or Meta writes.


1. Canonical Coverage
Stages: A1, A2, A3.
Contracts: C02, C03, C04.
Primary domain/core ownership: Advisor primary; Director frames; Context/Knowledge provide scoped truth; Experience handles interaction; Commercial/Billing is downstream, not a Core.
Dependencies: BP-00, BP-01, BP-02.


2. Functional Requirements
FR-03.1 Run adaptive Short Diagnosis until Minimum Sufficient Initial Understanding, not fixed question count.
FR-03.2 Skip known/retrievable information and capture corrections/Unknowns.
FR-03.3 Generate Strategy Initial showing what is understood, what it means, three material insights, recommendation, assumptions/Unknowns and what could change it.
FR-03.4 Include Route Recommendation as the final conclusion of Strategy Initial, never a separate Stage.
FR-03.5 Expose real professional value before payment.
FR-03.6 Present recommended Service Scope with included/excluded work and rationale.
FR-03.7 Separate Campainer service price from Media Budget, AI/production/provider costs where applicable.
FR-03.8 Record user commercial choice and payment/entitlement.
FR-03.9 Payment grants professional-work entitlement only and carries no Strategy/Creative/Execution authority.
FR-03.10 Return to A1/A2 when requested scope or new evidence changes professional meaning.


3. Non-Functional / Governance Requirements
Questions and recommendation must remain explainable and source-traceable; commercial UX must not manipulate professional recommendation; payment failures must not corrupt diagnostic/strategy state; journey must resume safely; mobile-first interaction should not degrade semantic visibility of assumptions/unknowns.


4. Conceptual Data Objects and Relationships
InitialUnderstanding; StrategyInitial; Insight; RouteRecommendation; ServiceOffer; ServiceScopeChoice; PaymentEntitlement; UserCorrection. StrategyInitial references the exact InitialUnderstanding/evidence version; RouteRecommendation belongs to StrategyInitial.


5. Proposed Concrete Schemas — DRAFT / NOT APPROVED
initial_understanding(id,scope_id,version,status,claim_refs,unknown_refs); strategy_initial(id,understanding_id,version,summary_ref,recommendation_ref,assumption_refs); insight(id,strategy_initial_id,ordinal,evidence_refs); route_recommendation(id,strategy_initial_id,route_kind,rationale_ref); service_scope_choice(id,user_id,route_ref,scope_ref,state); payment_entitlement(id,scope_choice_id,provider_ref,status,amount,currency). Pricing/provider fields DRAFT.
Schema rule: IDs, fields, enums, indexes and persistence mechanics remain DRAFT until separately approved. No inferred field is canonical merely because it appears here.


6. API / Integration Requirements
start/resumeShortDiagnosis; submitAnswer/correction; evaluateMinimumSufficiency; generate/reviewStrategyInitial; presentServiceOffer; selectServiceScope; createPaymentIntent; confirmEntitlement; handoffPaidScopeToA4. Billing callback cannot set authorization.


7. Prompt / Model / Tool Responsibilities
Advisor model asks decision-relevant questions and drafts Strategy Initial using BP-01 projections. It may recommend route/scope but not alter pricing contracts or claim payment authority. Human Review covers material Strategy Initial recommendation in pilot.
Prohibited: private chain-of-thought storage; silent authority expansion; turning Prior into Local Truth; silent strategy/brand/budget/measurement changes outside the owning Core.


8. UI / Workbench Requirements
Conversational/adaptive diagnosis; visible progress without fake fixed questionnaire count; Strategy Initial as professional deliverable with three insights and final Route Recommendation; clear scope/price separation; payment status; ability to correct material understanding before purchase.


9. Authority / Consent / Human Review Gates
A1/A2 contain no execution authority. User choice at A3 is commercial choice. Payment/entitlement must be explicitly labeled as not Strategy Approval, Creative Approval, Authorization or Launch. Material Strategy Initial recommendation receives Human Review in pilot.
Pilot default: 100% Human Review for material professional/execution decisions covered by this package.


10. Context / Knowledge Projection Interfaces
A1/A2 receive minimum business/offering/goal/current-state Context plus relevant scoped priors/evidence. A3 receives only selected route/scope and minimum facts needed to explain purchase; no broad Knowledge retrieval for payment processing.


11. Evidence / Event / Readback Requirements
Store question/answer source, corrections, material Unknowns, InitialUnderstanding version, Strategy Initial version/evidence basis, route rationale, user selection, offer version, payment provider reference/status and entitlement transition.


12. Metrics / Measurement Requirements
Journey quality: questions that changed decision, correction/reopen events, Strategy Initial review outcomes, route acceptance/defer/reject, payment completion/errors. Commercial conversion must not become a proxy for professional recommendation quality.


13. Failure / Recovery / Rollback / Semantic Return
Contradictory answer→targeted reopen; insufficient knowledge→Unknown/targeted question; payment failure→preserve A1/A2 and scope choice; scope conflict→Return to Advisor/Director; duplicate billing callback must be idempotent.


14. Security / Privacy / Multi-Business Isolation
Payment tokens handled by provider; avoid storing unnecessary payment data; Business scope isolation for all diagnostic/strategy artifacts; user can access only own scope and approved reviewer/operator roles.


15. Tests
Adaptive diagnosis stops without fixed count; known info skipped; Strategy Initial always contains route as conclusion; no payment before professional value display where canonical flow requires; service/media budget separated; payment creates entitlement but no authorization; failed/retried payment preserves state.


16. Acceptance Criteria
AC-03.1 User reaches Strategy Initial from Short Diagnosis using Minimum Sufficient Understanding.
AC-03.2 Three insights + Route Recommendation are part of the same Strategy Initial artifact.
AC-03.3 User receives substantive professional value before payment.
AC-03.4 Service price and Media Budget are visibly separate.
AC-03.5 Payment status is traceable and does not create live authority.
AC-03.6 A3 can hand off a paid/selected scope to A4 without losing prior evidence/Unknowns.


17. Migration / Compatibility
Archive/disable legacy fixed 45-question strategy flow as active requirement while preserving history; map existing short-diagnosis answers into new local claims where provenance is known; existing billing integration must be wrapped by entitlement semantics.


18. Deferred / Open Decisions
Exact question-selection algorithm, Strategy Initial presentation layout, route taxonomy, final pricing formulas/packages, billing vendor/API, exact monetary refund/cancellation formulas/fees/legal terms/provider dispute mechanics, exact payment-state enums.
Deferred items are not silently treated as defaults. Any blocker status must be explicit.


19. Traceability
Product Truth real value before payment + Progressive Diagnosis → Stage Truth A1/A2/A3 → Contracts C02/C03/C04 → BP-03 requirements/tests.
Every implemented requirement must map back to approved Truth/Core/Flow/Stage/Contract and forward to a test/evidence requirement.


20. Build Authority Gate
This package remains NON-EXECUTABLE until the Product Owner explicitly grants Build Authority to this package or to a governed release wave that names it.


21. OWNER-APPROVED ENTITLEMENT LIFECYCLE — F1 REMEDIATION
21.1 Governing contract. BP-03 consumes C04 v1.1. Payment/entitlement is a commercial prerequisite for paid professional work and never Approval, Authorization, Execution or Launch authority.
21.2 Cancellation/refund/chargeback do not erase completed professional work and do not rewrite historical Truth, Evidence, Human Review, Authority, execution history or Lineage.
21.3 A governed entitlement-state change may suspend or terminate future professional work not yet performed. If material professional work is already in progress, no new material stage, irreversible cost or new external commitment may begin until Human/Commercial Review resolves the entitlement state.
21.4 Chargeback/payment dispute changes only entitlement to continue professional work. It does not mint, revoke or retroactively rewrite live-action Authorization or prior review/execution state.
21.5 Every entitlement transition is auditable, scope-bound and version-bound and records the exact commercial event/source that caused it. Duplicate provider callbacks remain idempotent.
21.6 Exact monetary refund formula, fees, legal terms, provider-specific dispute mechanics and final payment-state enums remain Deferred. Build must not invent them.
21.7 Required tests: completed-work history survives cancellation; future-work entitlement suspends/terminates according to governed state; in-progress material work blocks new irreversible commitment pending review; chargeback cannot alter AuthorityRecord/HumanReviewRecord history; entitlement transition is scoped/versioned/auditable; duplicate callbacks are idempotent.
21.8 Acceptance additions. AC-03.7 Entitlement lifecycle cannot erase historical professional work or governance evidence. AC-03.8 Entitlement change cannot create or modify live-action authority. AC-03.9 Ambiguous/in-progress entitlement state fails closed for new material work pending Human/Commercial Review.
