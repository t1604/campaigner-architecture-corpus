0. PURPOSE


מסמך זה הוא Wave A Truth/Core Reconciliation עבור Complete User Context. הוא נשען על החוקה, Product Truth, Advisor Core, COMPLETE-USER-FILE-001-STAGE4-DRAFT, Professional Knowledge Foundation, Advisor–User Improvement Loop והכרעות/חידודים מאוחרים של בעל המוצר. הוא אינו מקדם אמת אוטומטית ואינו קובע Schema טכני.


1. ROLE OF THE CORE


Complete User Context מחזיק את האמת המקומית החיה, ההיסטורית, התחומה והמורשית על המשתמש, העסקים שלו, ה-Offerings, ההקשר הפעיל והמצב הנוכחי — במידה הנדרשת כדי ש-Campainer תוכל להבין, להחליט, לפעול, למדוד וללמוד בלי להתחיל מחדש ובלי לערבב הקשרים.


ה-Core אחראי לשמור ייצוג:
- חי ולא snapshot מת בלבד;
- מבוסס ראיות ומקור;
- תחום ל-Subject/Business/Offering/Account/Context הנכון;
- מתוזמן וניתן לריענון;
- מורשה לשימוש;
- ניתן לתיקון, הגבלה, ביטול וייצוא בהתאם לחוקה;
- ניתן להקרנה כ-Minimum Sufficient Projection לצרכנים מורשים.


2. WHAT THIS CORE IS NOT


Complete User Context אינו:
- אוסף כל מידע אפשרי על אדם או עסק;
- מאגר כל ה-Raw Data של Meta/CRM/Accounting/Documents;
- Knowledge / Evidence Core;
- Director;
- Advisor;
- Learning/Evolution;
- CRM חלופי;
- מנוע פסיכולוגי שמסיק מניע סמוי מאות התנהגותי;
- רישיון לערבב בין עסקים של אותו משתמש;
- רישיון לתת לכל בעל תפקיד את כל התיק.


3. ROOT DISTINCTIONS — CANDIDATE CORE TRUTH


3.1 USER ≠ BUSINESS ≠ BRAND ≠ OFFERING ≠ CAMPAIGN OFFER.
אותו אדם יכול להחזיק כמה עסקים; אותו עסק יכול להחזיק כמה Brands/Offerings; מידע אינו יורש תחולה אוטומטית כלפי מטה או לצדדים.


3.2 ACCOUNT/ORGANIZATION ≠ PERSON/CONTACT ≠ DECISION UNIT ≠ OPPORTUNITY.
במיוחד ב-B2B, תפקיד/סמכות/השפעה אינם מומצאים מהכותרת או מהיות העסק Enterprise.


3.3 EVIDENCE ≠ CLAIM ≠ ACTIVE MODEL.
אירוע/אמירה/מסמך/נתון אינם הופכים ישירות למסקנה פעילה ללא שכבת Claim/Interpretation מתאימה.


3.4 EXPLICIT USER TRUTH ≠ USER HYPOTHESIS ABOUT OTHERS.
המשתמש יכול להיות סמכות ישירה על מטרה, העדפה, מגבלה, בחירה עסקית והגדרת Desired Work שלו. הוא אינו הופך אוטומטית לסמכות על מניע לקוח, Intent סמוי או סיבת כשל שיווקי.


3.5 BEHAVIOR ≠ MOTIVE.
אות התנהגותי עשוי ליצור Hypothesis; הוא אינו אמת פסיכולוגית על האדם.


3.6 STRENGTH ≠ CONFIDENCE.
עוצמת דפוס והביטחון בכך שהדפוס אמיתי הם ממדים שונים.


3.7 CURRENT STATE ≠ BASELINE ≠ HISTORICAL STATE.
המערכת חייבת לדעת מה היה נכון לפני שינוי, מה נכון עכשיו ומה השתנה ביניהם.


3.8 CORRECTION ≠ USAGE RESTRICTION ≠ SUBJECT REASSIGNMENT.
“זה לא נכון”, “אל תשתמש בזה” ו“זה בכלל על אדם אחר” הן פעולות שונות.


4. SUBJECT / IDENTITY REGISTRY


כל מידע משמעותי חייב לדעת על מי או על מה הוא מדבר, או להישאר UNASSIGNED עד שיודעים.


Candidate subject families:
- User / account owner;
- Business;
- Brand;
- Offering;
- Campaign Offer;
- Customer/Account;
- Person/Contact;
- Lead;
- Opportunity;
- Decision Unit;
- Campaign;
- Asset;
- External party / other person;
- Unknown/Unassigned subject.


Core principle:
Information about one subject never contaminates another subject by convenience.


5. LOCAL CLAIM / STATE MODEL


Material local understanding should be representable with:
- subject;
- statement/value;
- source/evidence references;
- local truth status;
- confidence;
- scope;
- valid_from / valid_until;
- freshness;
- sensitivity;
- usage permission;
- allowed consumers;
- contradictions;
- correction state;
- history/version;
- reopen triggers.


Exact fields are Architecture candidates, not Core schema.


6. BUSINESS / OFFERING SCOPE AND INHERITANCE


Business-level facts may persist across Offerings only when their semantics genuinely belong to the Business.


Do not auto-inherit:
- campaign goal;
- desired customer definition;
- buyer state;
- journey;
- bottleneck;
- strategy;
- proof requirement;
- economics;
- capacity need;
- route;
- Golden Lead predictors.


Inheritance requires explicit scope semantics and may require verification.


Multi-business user rule:
Advisor continuity across businesses does not grant permission to mix business context, assets, customers, economics or learning.


7. GOALS / DESIRED WORK / SUCCESS CONTEXT


Complete User Context should preserve locally authorized business goals, priorities, Desired Work and meaningful constraints.


A goal may be:
- explicit and current;
- inferred candidate requiring reflection;
- superseded;
- paused;
- scoped to a specific Business/Offering/campaign/horizon.


Goal change must preserve history; a model-inferred “better goal” does not silently replace the owner’s goal.


8. BASELINE SNAPSHOT — WORKING CORE CANDIDATE


Before a material intervention, Campainer should be able to preserve the relevant starting state needed to interpret later outcomes.


Baseline Snapshot is not “copy the whole business.” It is a scoped, time-bound capture of the dimensions that can materially affect the outcome under review.


Depending on the decision, this may include:
- business goal;
- active Offering/Campaign Offer;
- current strategy/campaign state;
- current creative/offer/audience/route;
- current lead-handling process;
- CRM/tracking availability;
- response/follow-up/qualification state;
- capacity/serviceability;
- known economics;
- relevant Brand/Proof assets;
- measurement availability;
- known concurrent business changes;
- material Unknowns.


Every Baseline element should preserve Source + Scope + Time + Confidence/Status where applicable.


Purpose:
Allow later distinction between Campaign Change / Creative Change / Meta Change / Sales Change / Business Change / Market Change, instead of attributing all improvement or decline to advertising.


Exact Snapshot schema remains Architecture/Measurement work.


9. LEAD-HANDLING READINESS — LOCAL CONTEXT REQUIREMENT


Because Product Truth extends beyond lead creation, Complete User Context must be able to represent the business-side realization path when relevant.


At minimum, the system may need to know:
- where leads arrive;
- whether each lead is retained/tracked;
- who owns response;
- meaningful response process;
- follow-up behavior;
- qualification method;
- status progression;
- won/lost/disqualified/no-response semantics;
- lost reasons where available;
- ability to reconstruct what happened to prior leads;
- response/handling capacity.


Absence of CRM is not automatically a launch blocker. It may create a parallel Task/Intervention to establish minimum viable lead tracking.


Lead Handling data belongs locally; general response-time or qualification priors remain Knowledge, not Local Truth.


10. PROGRESSIVE DIAGNOSIS / MINIMUM SUFFICIENT UNDERSTANDING


Complete User Context is built progressively; it is not required to be “complete” before the first campaign.


Pre-first-campaign target:
Minimum Sufficient Understanding for a responsible professional decision and measurable first campaign.


The context should become deep enough to support, at minimum where relevant:
- current business objective;
- active Offering/Campaign Offer;
- working desired customer / Golden Lead definition;
- buying situation / buyer-state hypothesis;
- suspected Marketing Problem/Bottleneck;
- proof/offer/creative needs;
- lead handling / business realization readiness;
- executability/constraints;
- measurement plan;
- material Unknowns and risk.


Then stop asking when remaining unknowns do not materially change campaign-one strategy, audience, offer, creative, executability, risk or measurement.


After launch:
Reality → Evidence → targeted deeper questions → updated local understanding.


This principle does not canonize a fixed number of questions.


11. QUESTION / EVIDENCE ACQUISITION DISCIPLINE


Before asking the user:
- What decision depends on this?
- Is it already known?
- Can it be read from an authorized system/source?
- Can it be observed/derived with sufficient confidence?
- Will the answer materially change the decision?


If not, do not ask now.


User burden, privacy and opportunity cost are part of information-value judgment.


12. PREFERENCES AND WORKSTYLE


Preferences must preserve:
- explicit vs inferred origin;
- scope;
- confidence;
- duration/validity;
- exceptions;
- correction/withdrawal;
- “ask me each time” state where relevant.


Temporary behavior or one interaction does not become a permanent personality trait.


Form may adapt to user preference; Truth and professional standards do not.


13. DECISIONS / COMMITMENTS / OPEN OBLIGATIONS


The local context needs continuity not only of facts but of commitments.


Candidate local objects/relations include:
- user decision;
- recommendation accepted/rejected/deferred;
- user commitment;
- system commitment;
- open task/business task;
- responsible party;
- completion evidence;
- due/reopen condition;
- approval/authorization state;
- execution result.


Exact Runtime entities remain open.


14. INTERVENTION / BUSINESS CHANGE HISTORY


When the business itself changes, Metrics/Learning must know it.


Material interventions should preserve, at the appropriate layer:
- why the change was requested;
- supporting evidence/hypothesis;
- who authorized it;
- who executed it;
- when it changed;
- previous state;
- new state;
- measurement/outcome link;
- reopen/rollback condition where relevant.


Examples:
CRM adoption, follow-up process, response ownership, offer change, qualification process, capacity change, pricing/payment change, Proof/Asset creation.


Complete User Context owns the local fact/history that the change occurred. Knowledge owns the general professional basis; Metrics owns what was measured; Learning owns cross-case/generalization lifecycle.


15. UNKNOWN / GAP / CONTRADICTION


Local Unknowns are first-class and may persist across stages.


The context should preserve:
- what is unknown;
- why it matters;
- which decision it may affect;
- whether it blocks action;
- best closure route;
- temporary decision rule;
- trigger to reopen.


Contradictory local evidence is not silently resolved. Advisor may need Reflection/Verification when a material inference is about to affect strategy, goal, classification or action.


16. USER CORRECTION / CONTROL


When a material understanding is wrong, correction must propagate to affected projections and decisions.


User controls should support, according to constitutional scope:
- view/understand what Campainer believes;
- correct factual/interpretive errors;
- change a goal;
- object to an inference;
- restrict usage;
- reassign subject;
- revoke an optional preference;
- stop/exit;
- export/port owned information/assets where applicable.


Correction is not only UI. It must affect the active model and future decisions.


17. PRIVACY / MINIMUM NECESSARY CONTEXT


Existence of information does not justify universal access.


For every consumer, projection should reflect:
- purpose;
- decision need;
- minimum necessary information;
- sensitivity;
- permission;
- time scope;
- subject/business scope.


No role title grants full-file access.


Cross-business and cross-client use are distinct permission problems and must not be collapsed.


18. CONSUMER PROJECTIONS


Candidate projections, names not canonical:


Director Context View — goals, state, constraints, unknowns, decisions, risks, obligations and relevant local evidence.
Advisor View — relevant local truth/history/preferences/commitments needed to advise coherently.
Creative/Brand View — only business/brand/offering/asset/proof/constraint context needed for creative decision.
Meta/Execution View — only approved execution parameters, permissions, dependencies and current state required for execution.
Sales/Lead Handling View — lead/qualification/next-step/handling context.
Metrics/Learning View — baseline, intervention/change lineage, outcome semantics, local scope and relevant confounders.
User Transparency View — what Campainer understands, basis, status, allowed use and correction controls.


19. RELATION TO KNOWLEDGE / EVIDENCE


Knowledge/Evidence supplies general/scoped professional knowledge and evidence semantics.
Complete User Context supplies target-local facts, observations, decisions and living state.


Knowledge may generate a better question; local Context supplies the answer/evidence about this business.


General Knowledge → Better Hypothesis → Better Question → Local Evidence → Local Understanding.


Never General Knowledge → Local Fact.


20. RELATION TO ADVISOR / DIRECTOR


Director does not consume the whole file; it receives the minimum sufficient decision projection.
Advisor’s continuity depends on accurate Context but does not make Advisor owner of the file.


Advisor is responsible for reflecting material inferred understanding before fixing it as Local Truth when the uncertainty/impact warrants verification.


21. RELATION TO GOLDEN LEAD


Complete User Context supplies local business truth required by Golden Lead, including:
- owner desired work;
- business constraints;
- serviceability/capacity;
- Offering-specific facts;
- local economics where known;
- observed realized outcomes;
- local preferences/tradeoffs.


It must not collapse Desired Outcome Traits into predictive/targetable signals.


A trait the owner values may remain legitimate Business Truth even if Campainer cannot yet predict it pre-lead.


22. RELATION TO METRICS / LEARNING


Metrics needs exact local scope, baseline, timestamps, intervention/change history and outcome maturity.
Learning needs evidence lineage and local scope, but cross-business propagation remains governed separately.


A change in the business itself is a potential confounder and must survive into measurement interpretation.


23. DO-NOT-PROMOTE


Do not promote automatically:
- temporary preference into permanent profile;
- behavior into motive/personality;
- one business context into another business;
- one Offering’s journey/goal/Golden criteria into another Offering;
- owner belief about customers into buyer truth;
- absent CRM field into negative outcome;
- industry prior into local fact;
- old context into current context without freshness check;
- inferred goal over explicit owner goal;
- information about another person into account-owner profile;
- connected source into blanket permission to use all its data.

25. RECONCILIATION DISPOSITION


KEEP / CORE CANDIDATE:
- local living context responsibility;
- explicit subject/scope separation;
- evidence→claim→model layering;
- no overwrite without history;
- permission/minimum-necessary projection;
- correction/control;
- multi-business isolation;
- local Unknown/contradiction preservation;
- temporal/freshness discipline;
- local commitments/change history;
- distinction explicit owner truth vs hypothesis about customers.


EXPAND AS CORE CANDIDATE FROM PROFESSIONAL-KNOWLEDGE RETURN + OWNER DISCUSSION:
- Baseline Snapshot principle;
- Lead Handling / Business Realization state when relevant;
- Progressive Diagnosis / Minimum Sufficient Understanding;
- business intervention history and confounder tracking.


KEEP WORKING / ARCHITECTURE:
- exact modules/registers;
- exact claim schema;
- exact preference inference thresholds;
- exact snapshot fields;
- exact Runtime task/intervention entities;
- exact projection payloads.


REJECT AS CORE TRUTH:
- fixed 2-signal/3-event numeric rules as universal thresholds;
- confidence=0.76 example or any numeric pattern calibration;
- God-object/full-file access;
- automatic cross-business inheritance;
- personality/motive inference from behavior without evidence.


26. PROVISIONAL VERDICT FOR OWNER REVIEW


Complete User Context domain is ready for Core reconciliation. The strongest prior Stage4 architecture should be preserved at the responsibility/principle level, but its illustrative thresholds and internal module shape must not be silently canonized.


The Professional Knowledge return strengthens the need for this Core to carry Baseline, lead-handling/business-realization state, intervention/change history, Progressive Diagnosis and local-validation boundaries.
