0. PURPOSE
This candidate separates Meta platform truth from Execution Orchestration. Its purpose is to define what Campainer may treat as current platform/client capability, constraint, permission, state and freshness without allowing Meta convenience, guidance or technical possibility to choose marketing Strategy or create execution authority.


1. ROLE OF THE CORE
Meta Core owns the current, scoped and freshness-sensitive truth of what Meta permits, exposes, supports, constrains, requires or blocks for the relevant client/business/account/asset state.


It should be able to answer, when relevant:
- what is possible on the platform;
- what is available now for this client;
- what is enableable and what is required to enable it;
- what is conditional or requires a fresh live check;
- what is blocked and why;
- what can be read versus written;
- what permissions/asset relationships are currently present;
- what current state is observable and how fresh that observation is.


2. WHAT META CORE IS NOT
Meta Core is not:
- Strategy owner;
- Advisor or Director;
- Execution Orchestration;
- user permission/authority source;
- Golden Lead truth owner;
- Metrics/causal truth owner;
- Brand or Creative authority;
- a vendor-guidance-to-business-rule converter;
- a model that invents non-observable person-level Meta internals.


3. ROOT DISTINCTIONS
Capability ≠ Professional Decision ≠ Authority ≠ Execution ≠ Verified Live State.
Platform Guidance ≠ Marketing Truth.
Platform-Published Evidence ≠ Local Business Truth.
READ ≠ WRITE.
Visibility ≠ Ownership/Permission.
Connected Once ≠ Healthy Forever.
Signal Availability ≠ Signal Semantic Readiness.
Technical Success ≠ Marketing/Business Success.
Attributed Performance ≠ Incrementality.
Internal Platform Model State ≠ Advertiser-Observable Evidence.


4. META TRUTH VIEWS
Meta Core should preserve distinct views rather than one coarse “connected/ready” flag:
- Platform Possibility View;
- Client Current State;
- Client Enablement Space;
- Client Executable View;
- Pre-Strategy Possibility / Constraint View;
- Permission / Asset Relationship View;
- Freshness / Recheck State.
Exact schemas and enums are Architecture work, not Core truth.


5. PRE-STRATEGY POSSIBILITY / CONSTRAINT VIEW
By A08, Meta may inform the option space before Strategy is finalized. Conceptual states may include AVAILABLE NOW / ENABLEABLE / CONDITIONAL / REQUIRES LIVE CHECK / BLOCKED, but exact enums remain implementation-level.


Meta answers “what can responsibly be done here?” It does not answer “what should the business do?” Professional choice remains with the appropriate domain, Director and Advisor.


6. PERMISSION AND CLIENT STATE
Permission is a graph, not a boolean. Current executability may depend on app/access level, token/scopes, asset tasks, ownership/business relationship, business verification/app review, policy eligibility, subscriptions/webhooks, identity binding and object state.


A Page, account, pixel/dataset or asset being visible is not proof that Campainer may modify it.


7. FRESHNESS / RECHECK
Meta truth is freshness-sensitive. Recheck when material changes may have occurred in permissions, ownership, asset state, account review/policy, API/product behavior, integrations, route/objective, event source, or when readback contradicts prior state.


No universal refresh interval is promoted. Freshness must match the decision/action risk and platform volatility.
8. SIGNAL BOUNDARY WITH METRICS
By B05/B07, Meta/Technical owns whether a signal/event can currently be transported, observed, matched or technically used. Metrics/Measurement owns whether that signal has stable business semantics, sufficient maturity/coverage, appropriate outcome meaning and acceptable causal/selection limits for optimization or evaluation.


CAPI/CRM/event connectivity does not by itself establish signal quality or business readiness.
9. LIVE VALIDATION AND AUTHORITY
By F01, gated current-state Live Meta READ-ONLY validation is the next approved live validation class after the relevant Core/contract principle gates. This candidate does not itself initiate that validation and does not authorize WRITE, launch, budget changes, asset changes or production use.


Any material live write later requires scoped authority under C05/F02 and the controlled execution contract under F03.


10. SEMANTIC HANDOFF / RETURN
Meta Core must project technical possibility/constraint/state without changing professional meaning. If an approved intent cannot be realized faithfully, the technical path must return what is blocked, why, the current evidence/state, enablement path if any, and which alternatives preserve versus change meaning.


No Shadow Decision: technical feasibility never silently rewrites Strategy, Creative intent, scope, risk or authority.


11. PRIVACY / EXTERNAL SIGNAL BOUNDARY
External/public/platform-visible signals are market/platform intelligence, not person-level surveillance truth. Public ≠ unrestricted. No deanonymization or hidden person-level intent inference is promoted. Storage/use remains constrained by purpose, permission, minimization, law/policy and the approved cross-client governance principles.
12. DO-NOT-PROMOTE
Do not promote automatically:
- Meta recommendation/score → Strategy Truth;
- READ capability → WRITE capability;
- visible asset → ownership/authority;
- connected integration → healthy forever;
- technical event transport → semantic readiness;
- Match Quality → Golden Lead/business quality;
- attributed result → incrementality;
- technical success → business success;
- missing current setup → platform impossibility;
- non-observable internal model state → client evidence.
