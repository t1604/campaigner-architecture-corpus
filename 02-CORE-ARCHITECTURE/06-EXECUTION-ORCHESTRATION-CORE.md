0. PURPOSE
This candidate separates orchestration/execution responsibility from platform truth and professional judgment. It defines how Campainer coordinates an already-authorized professional action across systems, actors and providers without silently changing meaning, scope, risk or authority.


1. ROLE OF THE CORE
Execution Orchestration Core owns the faithful coordination of authorized actions. It receives a sufficiently closed semantic action contract and coordinates dependencies, actors/providers, technical operations, status/receipts, readback, failure/recovery/rollback and Semantic Return when faithful execution is not possible.


Its job is not to decide what is professionally desirable; its job is to make the authorized professional intent happen faithfully and verifiably.


2. WHAT EXECUTION ORCHESTRATION IS NOT
Execution Orchestration is not:
- Strategy owner;
- Advisor or Director;
- Meta platform-truth owner;
- Brand/Creative/Media professional decision owner;
- user-consent/authority source;
- local truth store;
- Metrics causal interpreter;
- Learning promotion engine;
- a permission to improvise around missing meaning.


3. ROOT DISTINCTIONS
Professional Decision ≠ User Choice ≠ Approval ≠ Authorization ≠ Execution.
Capability ≠ Authority.
Execution Receipt ≠ Verified Live State.
Technical Success ≠ Marketing/Business Success.
Technical Alternative ≠ Semantic Equivalence.
Retry ≠ Permission to repeat unsafe/non-idempotent change.
Failure ≠ Strategy Failure.
Provider Statement “Done” ≠ Completion Evidence.


4. INPUT — CLOSED SEMANTIC ACTION CONTRACT
A material action must be sufficiently closed before execution so orchestration does not need to invent professional intent.


The contract should preserve conceptually:
- intended action/outcome;
- target subject/object/scope;
- approved choice and authority state;
- evidence/decision reference;
- non-negotiable meaning/constraints;
- permitted technical freedom/substitutions;
- material cost/risk bounds where relevant;
- expected resulting state;
- verification/readback requirement;
- failure/return/rollback conditions.


Exact fields are Build-contract work.


5. AUTHORITY GATE
By C05/F02, orchestration must not infer authority from discussion, recommendation, payment, prior connection or vague assent. Material budget/launch/live/protected-Brand/business interventions require explicit scoped authority in P0.


If authority is absent, stale, ambiguous or mismatched to the target/action, orchestration returns the issue rather than executing.


6. FRESH PREFLIGHT
Before a material live action, orchestration obtains the current state needed to confirm that the authorized action remains executable and safe. Preflight may include target identity, permissions, dependencies, required assets/sources, policy/eligibility, current settings, measurement/readback availability and conflict with newer state.


Preflight is action-specific; no universal checklist is frozen in Core.


7. DEPENDENCY / ACTOR ROUTING
Orchestration coordinates the required sequence across internal components, Meta/other platforms, user/business actions and external providers. It should route the smallest sufficient task/projection to each actor and preserve dependencies and completion evidence.


By D06/E-governance, external providers receive minimum-necessary scoped access/data, not full context by role title.


8. CONTROLLED WRITE
By F03, material writes are controlled, bounded and traceable. Build contracts should support as appropriate exact target identity, before state, intended after state, bounded values, duplicate/idempotency protection, permission/authority check, receipt, retry safety and rollback/compensation semantics.


This candidate does not itself authorize any write.


9. POST-WRITE READBACK / VERIFICATION
A successful API/provider receipt is not enough when resulting live state can be checked. Orchestration should read back material changes where available to verify the correct object changed, intended state is present and no material visible divergence exists.


If readback is unavailable, uncertainty remains explicit; do not claim verified live state.


10. FAILURE / RECOVERY / ROLLBACK
Execution failure must be classified without automatically changing Strategy. Relevant classes may include transient failure, permission/eligibility failure, stale-state conflict, invalid object/parameter, platform review/wait, partial success, unknown live state and non-equivalent technical route.


Recovery must preserve intent and authority. Rollback/compensation is object/action specific; there is no universal delete/undo assumption.


11. SEMANTIC FIDELITY / NO SHADOW DECISION
By A09/C04, execution may choose a technical variant only when it is materially equivalent in intent, scope, business meaning, user approval, risk, privacy, material cost, expected outcome, measurement meaning and rollback implications.


If equivalence cannot be established, orchestration performs Semantic Return rather than silently substituting its own solution.


12. SEMANTIC RETURN
A return should preserve enough information for the upstream professional owner to decide:
- what was understood;
- what cannot be realized faithfully;
- why;
- current evidence/state;
- what is missing;
- available alternatives;
- which alternatives preserve meaning;
- which change Strategy/scope/risk/cost;
- who must decide/authorize next.


A returned action is a valid professional outcome, not a system failure.


13. HUMAN REVIEW / PILOT
By F05, material pilot professional/execution decisions remain under 100% Human Review until evidence supports narrower automation classes. Orchestration may automate mechanics inside an authorized contract, but it does not convert support/evidence into expanded sovereignty.


14. EVIDENCE / TRACEABILITY
Material execution should be traceable through Decision/Intent → User Choice/Approval → Authorization → Preflight → Execution Attempt(s) → Receipt/Readback → Final/Uncertain State → Measurement/Outcome → Learning/Next Decision.


Orchestration owns the execution segment and references adjacent segments; it does not swallow Context, Metrics or Learning ownership.


15. DO-NOT-PROMOTE
Do not promote automatically:
- recommendation → authorization;
- capability → authority;
- READ → WRITE;
- technical alternative → semantic equivalence;
- provider “done” → verified completion;
- write receipt → verified live state;
- retryable error → permission for unlimited retry;
- technical success → business success;
- execution failure → Strategy failure;
- orchestration convenience → professional decision.
